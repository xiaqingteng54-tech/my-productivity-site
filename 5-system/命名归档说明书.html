命名归档说明书

本说明书是知识库的唯一命名与归档依据。任何新笔记、新文件、新交付物进入本库前，先按本文件定名、定位置，再落盘。 归位由「文件整理 skill」执行；本说明书是它的规则源。

v1.1 变更（2026-11-13）：第五节 frontmatter 的空值写法由 - 改为 ""，并新增 5.1 空值红线与第九节自检动作。原因是 字段: - 会让 Quartz 构建报 bad indentation of a mapping entry，已实际导致 update-site.bat 连续发布失败。

一、设计原则

本库同时用两套方法，各管一件事。

方法管什么在本库的落点
PARA（Projects / Areas / Resources / Archives）文件放在哪目录结构
LLM Wiki（Karpathy：raw → wiki → schema，ingest / query / lint）知识怎么沉淀_index.md、log.md、概念页与法规页

三条硬规则：

  1. PARA 定位置，Wiki 定结构。 位置看”这件事有没有终点”，结构看”三个月后我还要不要用它”。
  2. 一个事实只存一处。 同一份法规、同一份问卷，只保留一个 source 文件，其余用双链引用，不复制。
  3. 文件名即检索入口。 不打开文件，只看目录也应知道这是什么、哪个辖区、什么时点。

0-Inbox/            未定型的碎片与原始材料（raw 层入口）
1-Projects/         有交付物、有截止时间的事

每个节点的固定文件

子目录放什么命名主语

跨领域概念放 3-Resources/；某概念已有主领域，就放该领域 Concepts/，别在两处各写一份。

三、命名规则

3.1 通用

  1. 结构固定为：{主体}-{限定}-{时点/版本}，从前到后逐级收窄；没有就不写，不留空占位。
  2. 分隔符只用半角短横线 -。不用空格、下划线、括号做分隔。
  3. 中文为主体语言；法规名、机构名、标准编号保留英文原文，不做中译回译（避免”通用数据保护条例”式歧义）。
  4. 禁用：新建笔记、未命名、随手记、副本、(1)、final、final2、最新、持续更新、~$ 临时文件。
  5. 长度 ≤ 60 字符；Quartz 会把文件名转成 URL，禁止 # ? / \ : * " < > |。
  6. 日期一律 YYYYMMDD（用于排序）或 YYYY-MM（用于周期）。状态不写进文件名，写进 frontmatter。

3.4 定名自检（三条，全过才落盘）

  1. 只看文件名，能否说出”哪个辖区、什么事、什么时点”？
  2. 文件夹名与文件名是否重复？（重复就删文件名里的重复部分）
  3. 是否带了”最新/最终/持续更新”这类会过期的词？（带就删，改由 frontmatter 的 status、updated 表达）

四、归档判定流程

任意一个新文件进来，按顺序问，命中即停：

Q1 它是我做的交付物，且有截止时间？
   └─ 是 → 1-Projects/{项目}/deliverables/
Q2 它是某个项目的原始输入材料？
   └─ 是 → 1-Projects/{项目}/sources/
Q3 它有明确归属领域（AML / 制裁 / Legal AI / 跨境），且是该领域长期口径？
   └─ 是 → 2-Areas/2.x/{Regulations|SOPs|Cases|Concepts}/
Q4 它跨领域、或只是外部资料、供以后引用？
   └─ 是 → 3-Resources/
Q5 它还没定型，只是碎片想法？
   └─ 是 → 0-Inbox/{YYYYMMDD}-{主题}.md
Q6 它是模板、说明书、脚本、看板、日志？
   └─ 是 → 5-System/

收尾规则：

  • 项目结束 → 整个项目目录平移到 4-Archives/，保持原相对路径，_index.md 的 status 改 已归档。
  • Inbox 不超过 7 天 → 超过即”要么归位、要么进 4-Archives/_stale/”，不留在 Inbox 里发霉。
  • 法规失效 → 不删，status 改 已失效，正文首行写”已被 XXX 替代”，链接指向现行版本。
  • 同一对象出现第二份 → 不建新文件，改为在原文件加”版本/分支”小节。

五、Frontmatter 规范

全库一套字段，英文键、中文值。（现状是两套：项目模板用 类型/状态，AML 模板用 type/area，必须统一。）

必填四项：title、type、area、status。外部来源必加 source_url。

5.1 空值红线（硬规则，违反即构建失败）

字段没有值时，一律写 ""（两个半角双引号，空字符串）。禁止写单独的 -。

原因：YAML 里 - 是列表项的开始符号。写成

解析器认为 jurisdiction 下面要跟一个列表，但下一行 product: 贵金属 回到了键值层级，层级对不上，Quartz 构建直接报 bad indentation of a mapping entry，update-site.bat 中断。

写法对照表：

场景正确错误
字段无值jurisdiction: ""jurisdiction: -
字段无值（另一种允许写法）jurisdiction:jurisdiction: -
字段本身是列表、当前为空tags: []tags: -
字段有单值product: 贵金属product: [贵金属]（非列表字段不要加方括号）
字段有多个值tags: [aml, 贵金属]多行 - 缩进写错

三条补充：

  1. 判断”这个字段是不是列表”看语义：tags、aliases 是列表，空值写 []；jurisdiction、product、status、source_url、version 是单值，空值写 ""。
  2. 不确定就用 ""，不要用 - 试探——"" 在任何字段上都不会导致解析失败。
  3. 正文里的 Markdown 列表（- 待办）不受此限制，本条只管 --- 之间的 frontmatter 区域。

5.2 新建 _index.md 时的固定模板

product 无值时写 ""，不得写 -；tags 无值时写 []。

兼容提醒：现有 首页.md 的 Dataview 查的是 status，而项目模板写的是 状态，两者不一致会导看板空白。统一后需把模板与已有项目笔记改一遍（见第七节）。

六、沉淀机制（Wiki 三动作）

归档解决”放哪”，沉淀解决”越用越值钱”。三个动作，由文件整理 skill 执行。

6.1 ingest（一份材料进库时）

  1. 源材料进 sources/ 或 3-Resources/，原文不加工；
  2. 写一页 source 摘要：发布机构、日期、URL、与我方业务的关系；
  3. 更新它触及的 2–3 个既有页（法规页 / 概念页 / SOP），有冲突就明写”与旧结论冲突，以 XX 为准”；
  4. 刷新所在 Area 的 _index.md；
  5. 5-System/log.md 追加一行：## [2026-11-09] ingest | {文件名} | 涉及页面：…

6.2 query（问答产出也沉淀）

  • 只在 wiki 层回答（法规页、概念页、案例页），不回读原始 PDF；
  • 有价值的回答（判定逻辑、对照表、口径）当场落成一页 Concepts/ 或 Cases/，不留对话里。

6.3 lint（每季度一次）

检查五类问题并出清单：

  1. 死链、孤页（无任何入链）；
  2. 被新法/新规替代但 status 仍写”现行有效”的法规页；
  3. 同一概念两页并存、结论不一致；
  4. _index.md 与实际文件不符；
  5. 长期滞留 Inbox 的碎片。

九、执行顺序（给 skill 的固定动作）

  1. 读本说明书；
  2. 判断文件类型 → 查第三节模板定名；
  3. 走第四节判定流程定位置；
  4. 补第五节 frontmatter，空值一律写 ""（列表字段写 []），禁止写裸 -；
  5. 执行第六节 ingest 三步（摘要页、更新既有页、刷新 _index 与 log）；
  6. 发布前自检：确认本次改动/新建的文件，frontmatter 内无 字段: - 写法（命令见第十节）；
  7. 输出一张”改了什么”清单：原名 → 新名、原位置 → 新位置、更新了哪些页；
  8. 涉及删除、移动、覆盖已有文件时，先列出待改清单，等确认再动手。

PowerShell（推荐）

CMD

无输出即可发布；有输出就按 5.1 改成 "" 或 []。
